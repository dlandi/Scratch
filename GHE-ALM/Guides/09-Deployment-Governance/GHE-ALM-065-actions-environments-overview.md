# How to Understand GitHub Actions and Environments at a Manager Level

**Guide ID:** GHE-ALM-065
**Audience:** Engineering Manager, Release Manager, Program Manager
**Primary role:** Engineering Manager
**Classification:** Manager Understands
**Estimated time:** 20-25 minutes one-time read
**Required permissions:** Repository: Read

**Prerequisites:**

- Access to a repository that uses GitHub Actions for build or deployment.
- Familiarity with GitHub issues, pull requests, and branches.
- Read GHE-ALM-001 first to understand how repositories, releases, and deployments fit together.

**When to use this guide:** Read this when you need to interpret deployment status, talk to engineers about CI/CD outcomes, or sign off on a release without writing or reviewing YAML.

**When not to use this guide:** Do not use this guide to author workflow files, configure environment protection rules, or debug a failing pipeline. Those tasks belong to engineers and repository administrators.

## Outcome

By the end of this guide, you will have produced:

- A working mental model of workflows, jobs, runs, environments, and deployments.
- A short glossary you can use in standups and release reviews.
- A set of decision rules for reading run status and deployment history.

## Before You Start

- Identify one repository in your product that runs GitHub Actions.
- Open the repository's **Actions** tab and the repository's **Deployments** view (or the environments list under **Settings**) so you can match the concepts in this guide to real screens.
- Confirm with engineering which environments your team uses (typical names include `dev`, `qa`, `staging`, `production`).

## Steps

### 1. The five objects you need to recognize

GitHub Actions is built from a small number of named objects. Learn these five and you can read most of what the Actions tab shows.

- **Workflow.** An automation file stored at `.github/workflows/<name>.yml` in the repository. The file lists triggers (for example, push to `main`, pull request opened, manual dispatch, scheduled time) and the work to perform. You do not edit this file. You do need to know it exists and that engineering owns it.
- **Job.** A unit of work inside a workflow. A workflow can contain one job or many. Jobs run on a runner, which is a virtual machine that executes the steps. Jobs can run in parallel or in sequence. A job has its own status.
- **Step.** An ordered command inside a job. Steps are the smallest unit you will see in the run logs. You rarely talk about steps in a management conversation; you talk about jobs.
- **Workflow run.** A single execution of a workflow. Each run has an ID, a triggering event (commit SHA, pull request, tag, manual dispatch), a duration, and a status. The Actions tab is a list of runs.
- **Environment.** A named deployment target configured in repository **Settings** under **Environments**. Common names are `production`, `staging`, `qa`, `dev`. An environment can carry secrets, protection rules, required reviewers, wait timers, and branch or tag restrictions. When a job deploys to an environment, that fact is recorded as a deployment.

### 2. Workflow run status, in plain language

Every workflow run shows a status icon next to it. Read the icon, not the YAML.

| Icon or label | Meaning | What you do |
|---|---|---|
| Green check, **Success** | The run finished and every required job passed. | Nothing. The build, tests, or deployment succeeded. |
| Red X, **Failure** | At least one required job failed. | Open the run, find the failed job, read the first error line. Ask the assignee or the PR author to investigate. |
| Yellow dot, **In progress** or **Queued** | The run is currently executing or is waiting for a runner. | Wait. If a run sits queued for a long time, ask engineering whether runners are available. |
| Grey, **Cancelled** | Someone cancelled the run, or a newer run superseded it. | Usually fine. Confirm whether a follow-up run was started. |
| Brown or orange, **Skipped** | A job was intentionally not executed because its conditions were not met. | Read the job name. Skipped is normal for conditional jobs. |
| Purple, **Waiting** | A deployment job is paused for required reviewer approval, a wait timer, or a branch/tag restriction. | Action may be needed. See GHE-ALM-067. |

Jobs inside a run carry the same statuses. A workflow run is green only when every required job is green.

### 3. Environments and deployments, in plain language

A workflow can do many things: lint code, run tests, build artifacts, publish a release. A deployment is a specific kind of outcome. When a job targets an environment, GitHub records a deployment fact: this commit shipped to that environment at this time, by this actor, with this status.

You can see deployments in two places:

- The repository **Deployments** view (linked from the right sidebar of the repository home page) lists current and historical deployments per environment.
- The **Environments** list under **Settings** shows each environment, its current active deployment, and its protection configuration.

A deployment has:

- A target environment, for example `production`.
- A commit SHA or tag that was deployed.
- A status: `in_progress`, `success`, `failure`, `error`, or `inactive` (replaced by a newer deployment).
- An actor: the user or the workflow that initiated it.
- A timestamp.

Environments can carry protection rules. The three you need to recognize:

- **Required reviewers.** A named user or team must approve before the deploy job runs. Until approval, the job sits in the `Waiting` state.
- **Wait timer.** A delay (for example, 10 minutes) between approval and execution. This gives operators a window to cancel.
- **Deployment branch and tag rules.** Only commits from certain branches (for example, `main` or `release/*`) or matching tags can deploy to the environment. A push to a feature branch cannot reach production by accident.

GHE-ALM-068 covers requesting these protection rules. GHE-ALM-069 covers reading branch and tag restrictions.

### 4. Decision rules for the manager

You do not need to read YAML. You do need decision rules.

- **Green workflow run on `main`:** the change is built and tested. Safe to keep moving.
- **Red workflow run on a pull request:** do not approve a merge until the PR author addresses the failure. Linked checks on the PR will show the same red.
- **Yellow run that has been in progress longer than the team's normal build time:** ask whether runners are queued or whether a step is hanging.
- **Required reviewer pending on a deployment to `production`:** someone with reviewer rights must approve. If you are the designated approver, follow GHE-ALM-067. If not, identify the approver and notify them.
- **Deployment shows `success` for the expected commit on the expected environment:** release reached that environment. Combine with GHE-ALM-066 to confirm history.
- **Deployment shows `failure` on `staging` while `production` shows `success` for an older commit:** the new release did not advance past staging. Production is still on the previous version. This is the single most common misread.
- **Deployment to `production` from a branch that is not `main` or `release/*`:** verify with engineering. The branch and tag rules may have changed, or someone bypassed them.

### 5. Glossary you can use in conversation

| Term | One-line definition |
|---|---|
| Workflow | The automation file that defines triggers and jobs. |
| Job | A unit of work in a workflow that runs on a runner. |
| Run | A single execution of a workflow with a status and logs. |
| Runner | The machine that executes job steps. GitHub-hosted or self-hosted. |
| Environment | A named deployment target that can carry secrets, reviewers, and protection rules. |
| Deployment | A recorded fact that a workflow shipped a commit or tag to an environment. |
| Required reviewer | A user or team whose approval is needed before a deployment job runs. |
| Wait timer | A configured delay between approval and execution. |
| Branch or tag rule | A restriction on which branches or tags can deploy to an environment. |
| Status check | A pass/fail signal from a job, surfaced on the related pull request. |

### 6. Worked example

The release manager at `acme-payments` is preparing release `2026.05.0` for the `checkout-service` repository. She opens the **Actions** tab and sees three recent runs against the release branch `release/2026.05.0`:

1. The first run, triggered by a push, is green. Build and tests passed.
2. The second run, triggered automatically after merge, is green for the `build` and `deploy-staging` jobs. The `deploy-production` job shows **Waiting**.
3. There is no third run yet.

She opens the **Environments** list and sees:

- `staging`: active deployment is commit `a1b2c3d` from `release/2026.05.0`, status `success`, deployed 14 minutes ago.
- `production`: active deployment is commit `9f8e7d6` from `release/2026.04.1`, status `success`, deployed 9 days ago. A new deployment for `a1b2c3d` is queued with status `waiting`.

She concludes:

- Build and staging deployment for `2026.05.0` succeeded.
- The production deployment is paused on required reviewer approval. The current production version is still `2026.04.1` until that approval lands.
- The next action is for the designated approver (in this case, herself) to follow GHE-ALM-067 and approve the protected deployment, after release readiness review (GHE-ALM-046) is complete.

She did not open a single YAML file.

## Validation Checklist

- [ ] You can name workflow, job, run, environment, and deployment without checking notes.
- [ ] You can read a workflow run status icon and translate it to action or no action.
- [ ] You can locate the Deployments view and the Environments list for one of your repositories.
- [ ] You can distinguish a queued run from a deployment waiting on a required reviewer.
- [ ] You can tell which commit is currently active in `production` for one of your repositories.

## Common Mistakes

- Treating a green build as proof that production was updated. A green build only means the run succeeded; check the deployment for the target environment.
- Assuming `Waiting` means broken. Waiting usually means awaiting a required reviewer, a wait timer, or a branch rule, not a failure.
- Asking engineering to "rerun the YAML" when the issue is a missing approval or a branch restriction. Read the environment first.
- Conflating workflow runs with deployments. One workflow run can produce zero, one, or several deployments depending on its jobs.
- Reading only the most recent deployment to an environment. The active deployment may be older than the most recent attempt if the most recent attempt failed.

## Escalation Path

- GitHub administrator: when runners are persistently queued, when self-hosted runner capacity is needed, or when organization-level Actions policy is in question.
- Repository administrator: when environment protection rules need to be created or changed, or when branch and tag restrictions need to be adjusted.
- Engineering lead: when a workflow run fails and the cause is not obvious, or when deployment behavior does not match what the team expects.
- Release manager: when a deployment is waiting on required reviewer approval and the designated approver is unavailable.
